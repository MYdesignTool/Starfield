# PERF-11：参数增量与删除长延迟分析

Owner反馈：126/115删除没有看到错误，但体感需5–10秒；建议修改哪个节点/参数就提交哪个节点/参数。本轮先分析与离线计数，产品和安装保持126/115，未操作AE/工程。

## 已确认的调用链

参数增量入口已经存在：`NodeGraphSync.cpp`从USER_CHANGED_PARAM构造`NativeEdit{uuid,node_kind,parameter_index,value_kind,value,additional_fields}`，直接调用`commit_native_graph_edit`，没有把整图从浏览器传一遍。问题在后端：`NativeGraphCommit.cpp`仍读取主效果控制、旧ARB，调用`compile_native_node_graph`；后者遍历所有作者，读取每个节点的参数/曲线/布局/连接，重新生成图及记录，然后处理整批绑定、资源、快照与发布验证。

需要纠正一个区别：普通参数编辑遇到相同且启用的表达式时，现有代码已经跳过表达式重写；不是每次参数修改都重新编译全部表达式。但仍读取无关作者、打开/检查所有有效绑定。只把消息改名为“参数提交”不会消除这些工作。

删除路径更重，两种顺序必须区分：面板原生delta先保护作者并收敛连接、publish ACK，再物理删除、最终绑定刷新、释放guard；观察式AE Clear先capture/guard，再让AE物理Clear，按实际消失UUID收敛连接、compile/publish，然后最终绑定刷新、释放guard。两者保留既有126保护。`NativeBindingTransaction::install`的`sources_removed`会关闭整个绑定集合的同文本快路；最终`refresh_panel_graph_bindings`再以`force_refresh=true`重建最终依赖。所有仍存活绑定在物理parade变化后的有效性，是先前516修复的一部分。

## 最具体的大开销：未使用零值槽被当作退休槽

`Parameters.cpp`为512个Native Render Input清零PF_ParamDef后注册，没有设置特殊默认值，所以未使用槽是零值、空表达式、禁用。最终绑定刷新遍历当前图未占用的槽：只要基础值有限且非unavailable，并且是本插件表达式或“禁用且空表达式”，就加入退休集合。默认从未占用的零值槽也满足这个条件。

`retire_after_publication`在force_refresh下还会写一次禁用的`value;`再清空，保证真实退休槽产生文本转换。结果是未使用槽也发生两次表达式写入，而不是仅一次便宜的空值检查。这是明确的潜在浪费，不是从Stardust行为推测而来。

仅改Particle Size的241次读取，分布为main30、Emitter71、Particle92、Force48；无关的Emitter和Force共119次。这个数据直接支持按目标节点/参数减少作者读取。最终刷新还伴随591次SetExpressionState、512次SetStreamValue（原默认零值夹具）。

这里“value读取”是AEGP_GetNewStreamValue的总调用次数，包括ARB、点、颜色等类型，不是241个纯标量。未读取现场AEP的实际占用槽清单，79/433及1024写入只描述这个受控3作者夹具，不声称现场工程也有同样分布。

反事实只是夹具控制：433个槽由夹具历史保证从未属于作者。没有给AE项目写sentinel，没有修改Parameters默认值，更不建议把项目所有零值槽重置。真实已退休绑定的有效值也可能是0；之前保护旧代交接和in-flight图所需的槽必须保留。158比1024少约84.6%是表达式写入调用量差，不是AE删除速度提升比例；本轮没有端到端AE计时，也没有模拟整次真实Clear的耗时。

可复现：`node artifacts/perf-11-20261031/prepare-budget.cjs`，然后在checkout执行`artifacts\perf-11-20261031\compile.cmd`。首个生成夹具有签名/变量名错误，原日志保留；修后完整重编实际生产对象成功，对照只重编计数夹具并链接同一批对象，最终2844检查/0失败。生成器、RSP、源码、对象、JSON与日志都在该目录。SDK夹具不是AE模拟器，不能据此宣称真实依赖重建资格。

## 5–10秒目前能解释到哪一步

可确认的重工作是整批绑定重建及512槽退休扫描；它们足以作为第一优先级计量对象，但调用量不能直接证明现场5–10秒的占比。现有journal共13306条（13242 render/64 graph-command，两个PID），Clear只记完成结果，没有请求入队、开始执行、捕获、发布、最终绑定、后读的同一次操作时间。相邻两条用户操作的间隔不能当作单次删除耗时；部分记录也缺工程和墙钟上下文，不扩大为当前测试事件判定。

冻结日志含3次已提交、无cleanup/undo错误的Clear完成，以及1次capture阶段516且未dispatch的记录；缺少工程/墙钟关联，不能将其归到本次5–10秒反馈或据此否定Owner的“本次未报错”。原始记录与摘要均保留，未选择性删除失败记录。

队列也有可核实的延迟来源：SDK的idle `max_sleepPL`单位是1/60秒；当前空队列上限请求30即约500ms，队列已有后续工作才请求1。删除及之后的展示快照可能跨多个idle；AE忙时仍可进一步推迟，500ms不是保证的实际调度上限。WebView入队路径未发现主动CauseIdle唤醒调用。现有资料不足以说排队就是5–10秒的主要原因。

画布反应也晚：面板原生Delete分支设置pending后直接请求Host，直到正回执及完整getGraphSnapshot都回来才更新画布。当前没有“已接收删除、正在处理”的立即局部预览。AE Clear的原生入口又是另一条同步路径，不能只改浏览器预览便宣称覆盖所有入口。

## 建议的下一轮实现边界

优先级一是删除的**精确槽归属与分阶段计量**：在同一次已验证UI操作内记录旧图、新图的有效槽和确实退休槽，保持仍存活绑定的126依赖刷新；从未拥有的槽不进入退休重编译。旧版本/冷启动/未知归属应保留既有完整回退。仅凭0/空文本/当前图不含该槽不能证明它从未被旧图使用，必须解决历史退休槽与旧代缓存的有效性证明；必要的持久化版本变化须先明确迁移，不能暗改schema。计量使用有界内存阶段时间，操作结束后一次写出，不把每个stream读写都记文件。至少区分queue wait、pre-clear capture、compile、bindings、physical clear/delete、final refresh、panel snapshot；同操作ID关联，成功和失败都保留。

优先级二是**目标节点重建，再缩到参数**：复用已有NativeEdit，读取上一份已确认图/原生记录，只更新目标UUID对应的字段或目标节点，再用已有原始记录回放/数值转换重建该节点。C++本地图校验/小块序列化可以保留，先减少昂贵的AE suite遍历。参数到原生磁盘索引/多分量/单位换算使用现有权威映射，不另写一套易失配的转换。callback的params[]可提供本节点的已送达值，但不持有其句柄跨回调。

首批白名单可研究Size/Opacity/Color、Force数值等不改变拓扑/资源/绑定布局的编辑；应按实际副作用分类，不能按“都是数字”分类。曲线/渐变作为目标节点的一个有界bank，activation additional_fields一并提交。Motion Type/Prefix、Auxiliary模式、Particle Shape扩展bank、Texture/Model/Transform引用等保留完整特殊路径。binding布局/归属不变时避免重建表达式；新增/删除/重接、容量变化或证明不成立时回退完整发布。

必须先证明缓存的新鲜度：project/renderer身份、保存图revision/CRC、author generation、几何/时间相关换算、Undo/redo、外部AE/脚本编辑、别名表达式被改变与资源更换。只缓存结构/记录，不能把某一帧的动画求值当常量。渲染继续使用不可变数值快照，不能在worker上调用AEGP，也不能原地修改正在渲染的Core图。参数影响的下游模拟仍需失效，增量提交并不等于只重新计算一个节点。

优先级三是**立即编辑反馈**：先在本地验证删除候选并显示pending结果，明确区分未提交/已提交/未知，失败按实际commit点恢复或重新读取；正回执后只补变化节点/连接与最小revision信息。必要的作者新鲜度刷新可延后到下一次manifest规划。它解决“等很久才看到反应”，但须与真实后台耗时优化分别报告，不能用动画掩盖慢事务。

本轮不部署、未取消现有发布ACK、旧代交接、新绑定检查或失败guard。产品仍为已验收的原生126/面板115。实施前应先对上述归属/缓存/失败边界做独立设计审校，再用阶段计量证明实际瓶颈，避免再以全图确认替代精确依赖模型。
